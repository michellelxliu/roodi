Every request is different. Serve it that way.

Roodi is an ML inference provider that works out what kind of request it has received and serves it accordingly. Today most stacks serve every request the same way. Roodi picks the model, hardware and serving strategy for each one.

The problem

A one-line autocomplete, a 100k-token document summary and a multi-step reasoning task have very different needs. When all three get the same model, batch and GPU, latency-sensitive traffic waits behind long jobs, and simple requests run on hardware sized for the hardest ones.

How Roodi works

A lightweight classifier sits in front of the serving fleet and profiles each request before it is scheduled.

01 · Profile

Characterize the request

Estimate its input and output length, task type, reasoning depth and latency sensitivity.

→
02 · Decide

Choose a serving plan

Pick the model size, hardware pool, batching and caching strategy that fit that profile.

→
03 · Serve

Run and learn

Serve the request, measure the outcome and feed it back so later decisions get better.

What Roodi looks at

These request characteristics drive the serving decision:

  • Prompt length
  • Expected output length
  • Shared prefix / cacheability
  • Task type
  • Reasoning depth
  • Latency vs. throughput priority
  • Quality requirement

What it changes

Right-sized models

Easy requests go to smaller, faster models, and hard ones go to models that can handle them.

Smarter scheduling

Interactive traffic is kept apart from long batch jobs, so short requests don't queue behind long ones.

Better cache use

Requests that share a prefix go to the same place, so the KV cache gets reused instead of recomputed.

Hardware fit

Prefill-heavy and decode-heavy work are each placed on the hardware that suits them best.
